# OCR 引擎技术选型对比报告（标准版）

- 文档日期：2026-04-04
- 输入文档：[需求分析文档](../requirements/2026-04-01-zupu-requirements-analysis.md)、[整体技术选型报告](./2026-04-01-zupu-tech-selection-report.md)
- 适用阶段：V0.2 迭代 — OCR 引擎升级
- 选型范围：OCR 识别引擎（针对吊线形式纸质族谱）

---

## 1. 背景与目标

### 1.1 业务背景

本系统的核心链路为"**手写纸质族谱图片 → OCR 识别 → 人工校对 → 结构化入库**"。V0.1 MVP 阶段使用了基础的 PaddleOCR（`lang="ch"`，通用行检测+识别），但在实际使用中发现以下关键问题：

1. **版面特殊性**：用户的纸质族谱采用**吊线形式**（悬挂式世系图），即以竖线连接父子关系、横线连接同辈兄弟。这种布局**不是标准的文档排版**，通用 OCR 无法理解其拓扑结构。
2. **文字方向复杂**：族谱中姓名常为竖排书写（繁体/简体混排），且存在批注、生卒年等小字附注。
3. **当前实现的局限**：`apps/ocr-service/main.py` 仅将所有识别文本拼接为一个 `raw_text` 字段，丢失了所有空间位置信息和层级关系。

### 1.2 选型目标

1. 从 OCR 识别结果中，**自动或半自动还原出族谱的层级树结构**（父子/兄弟关系）。
2. 准确识别竖排中文、手写体、繁体字等特殊文本。
3. 在现有架构（独立 Python OCR 服务 + HTTP API）下可平滑替换。
4. 部署资源可控（单机/小型 GPU 或纯 CPU 可运行）。

---

## 2. 需求约束摘要

来自需求文档与实际场景的关键约束：

1. **输入类型**：手机拍照/扫描的吊线式纸质族谱图片（可能存在弯曲、阴影、折痕）。
2. **文字特征**：竖排中文为主，简繁混排，手写体与印刷体并存，部分含生卒年阿拉伯数字。
3. **输出要求**：需要文字内容 + 空间坐标，最终还原为结构化的族谱成员列表及层级关系。
4. **部署约束**：1-2 人团队运维，优先 Docker 容器化部署，可接受 GPU（8GB+ 显存）或 CPU-only。
5. **成本约束**：优先开源免费方案，避免按调用量收费的云 API。
6. **延迟要求**：单张图片处理延迟可接受 5-30 秒（异步任务模式，非实时）。

显式假设：
1. 用户可接受"OCR + 人工校对"模式，OCR 不要求 100% 准确。
2. 每批次处理图片数量一般在 10-50 张以内。
3. 团队可接受在 Python 服务中引入额外依赖（如 PaddlePaddle、Transformers 等）。

---

## 3. 候选方案说明

### 候选 A：PaddleOCR-VL-1.5（多模态视觉语言模型）— 端到端方案

- **模型**：PaddleOCR-VL-1.5（0.9B 参数）
- **架构**：NaViT 视觉编码器 + ERNIE-4.5-0.3B 语言模型
- **核心能力**：将文档图片直接解析为结构化 Markdown/JSON，具备版面理解、阅读顺序重建、表格/公式/印章识别等端到端能力
- **调用方式**：
  - 云端异步 Job API：`POST https://paddleocr.aistudio-app.com/api/v2/ocr/jobs`（提交任务 → 轮询 → 获取 JSONL 结果）
  - 云端同步 API：直接返回结果（适合单页场景）
  - 本地推理：`from paddleocr import PaddleOCRVL; pipeline = PaddleOCRVL(); output = pipeline.predict(img_path)`
- **输出格式**：Markdown（含层级标题）或 JSON（含区域坐标与文本）
- **已具备条件**：项目已拥有 PaddleOCR 云平台 API Token，可免费调用云端 API（无需本地 GPU）

适配特点：
1. 模型具备"全局理解"能力，可通过 Prompt 指令引导提取族谱的层级关系。
2. 对竖排、弯曲、倾斜等复杂场景原生支持，无需额外预处理。
3. 单一模型即可完成"检测 + 识别 + 结构化"全流程，开发和维护成本最低。
4. 云端 API 模式无需本地 GPU，极大降低部署门槛。

### 候选 B：PP-StructureV3 + PP-OCRv5 管线（模块化方案）

- **版面分析**：PP-DocLayoutV3（实例分割，支持多边形定位）
- **文字识别**：PP-OCRv5（端到端精度提升 ~13%，支持竖排方向分类）
- **管线组合**：`from paddleocr import PPStructure; engine = PPStructure(table=True, ocr=True)`
- **输出格式**：区域列表（含类型、坐标、文本内容）

适配特点：
1. 模块化架构，各组件可独立替换与微调。
2. PP-DocLayoutV3 支持多边形检测，能框定弯曲/倾斜的文字区域。
3. PP-OCRv5 手写识别精度大幅提升，且内置文本行方向分类器。
4. 需在后处理阶段编写自定义逻辑，根据坐标位置还原层级关系。

### 候选 C：当前方案维持（PaddleOCR 通用模型，基线）

- **模型**：PaddleOCR（`use_angle_cls=True`, `lang="ch"`），即当前 `main.py` 使用的方案。
- **架构**：PP-OCRv4 检测 + 识别 + 角度分类三模块
- **输出格式**：逐行文本 + 置信度

适配特点：
1. 已在项目中集成，无需额外开发。
2. 无版面分析能力，不理解吊线结构。
3. 竖排支持有限，需手动旋转预处理。
4. 适合作为性能/精度对比的基线。

## 4. 评估维度与权重

根据本次选型的特殊性（族谱吊线结构还原为核心需求），调整权重如下：

| 评估维度 | 权重 | 说明 |
|---|---:|---|
| 功能匹配度 | 0.40 | 能否准确识别竖排手写文字，并还原吊线层级关系 |
| 开发效率 | 0.30 | 集成到现有架构的工作量、后处理逻辑复杂度 |
| 可维护性 | 0.30 | 模型升级便利性、组件可替换性、调试难度 |

总分公式：

$$
TotalScore(option)=\sum_{i=1}^{n}(Weight_i \times Score_{i,option})
$$

其中 Weight 使用小数（如 0.4, 0.3, 0.3），Score 为 1-5。

## 6. 风险与不确定性

### 6.1 PaddleOCR-VL-1.5 对吊线结构的理解能力（候选 A）
- **不确定性**：PaddleOCR-VL-1.5 主要针对标准文档（论文、合同、财报）训练，吊线族谱属于罕见版面类型，模型可能无法正确理解连线语义。
- **影响**：若理解失败，输出的 Markdown/JSON 可能是扁平文本而非层级结构。
- **应对**：先用 3-5 张真实族谱图片进行 Smoke Test；若效果不佳，可通过 Prompt Engineering 或少量 Fine-tune 优化。

### 6.2 GPU 显存与推理性能（候选 A）
- **不确定性**：0.9B 模型实测推理约需 4GB+ 显存；在 CPU-only 环境下推理速度可能超过 60 秒/张。
- **影响**：部署成本上升或用户等待时间过长。
- **应对**：优先申请 GPU 实例（如云平台 T4/A10）；备选方案为使用候选 B 的 CPU 推理模式。

### 6.3 坐标后处理逻辑复杂度（候选 B）
- **不确定性**：吊线族谱的排版规则多样（有些从右到左、有些从左到右、世代间距不固定）。
- **影响**：基于坐标的层级还原算法可能需要针对不同族谱格式进行适配。
- **应对**：先针对用户最常见的 1-2 种族谱模板开发算法；后续引入 LLM 辅助校正阅读顺序。

### 6.4 PaddlePaddle 环境兼容性
- **不确定性**：PaddlePaddle 在 Windows 上的 CUDA 兼容性偶有问题。
- **影响**：本地开发调试体验差。
- **应对**：统一使用 Docker 容器部署 OCR 服务，隔离环境依赖。

## 7. 推荐结论与适用条件

### 推荐方案：候选 A — PaddleOCR-VL-1.5（多模态端到端方案）

推荐理由：
1. **功能最契合**：唯一能从语义层面理解族谱版面结构的方案，不需要手写复杂的坐标推算逻辑。
2. **开发成本最低**：3 行 Python 代码即可完成调用，输出直接可用于结构化入库。
3. **面向未来**：多模态 VLM 是文档处理的发展方向，后续可平滑升级到更强的模型版本。

### 次选方案：候选 B — PP-StructureV3 + PP-OCRv5（模块化管线方案）

适用条件：
1. 候选 A 的 Smoke Test 效果不理想（吊线结构无法被正确解析）时。
2. 部署环境无 GPU 或显存不足，需要轻量 CPU 推理时。
3. 需要对特定环节（如手写体识别）进行针对性微调时。

### 暂不建议：候选 C — 当前 PaddleOCR 基础方案

不推荐理由：
缺乏版面分析能力，无法满足"**从吊线族谱图片中还原层级关系**"的核心需求。仅适合继续作为回退/降级基线。

### 实施路径建议

1. **第一步（验证）**：搭建 PaddleOCR-VL-1.5 测试环境，用 3-5 张真实族谱图片做 Smoke Test。
2. **第二步（评估）**：根据 Smoke Test 结果决定采用候选 A 还是候选 B。
3. **第三步（集成）**：修改 `apps/ocr-service/main.py`，替换核心识别逻辑。
4. **第四步（后处理）**：开发结构化提取与校对映射逻辑，对接前端 OcrPage。

## 附：需求追溯说明（关键结论依据）

1. 选型聚焦吊线识别：来源于用户确认的纸质族谱为吊线形式。
2. 推荐多模态端到端：来源于需求中"OCR 识别后逐条校对并入库"的流程需要结构化输出。
3. 保留模块化备选：来源于需求中"OCR 服务可替换"的架构设计原则。
4. GPU 需求评估：来源于非功能需求中的异步任务处理模式（可容忍较长延迟）。
